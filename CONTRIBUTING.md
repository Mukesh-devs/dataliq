# Contributing to BigView

Thanks for helping! Bug reports, ideas, documentation and code are all welcome.

## Reporting a bug or asking for a feature

Open an issue with what you did, what you expected and what happened instead. For a file
that doesn't open or looks wrong, say its format, size and (if you can) share a few lines
that reproduce it: BigView never uploads anything, so we only see what you attach. Help ›
About shows the BigView and DuckDB versions; the log is in the app's data folder
(`logs/bigview.log.<date>`).

## Setting up

Install the prerequisites listed under "Building from source" in the [README](README.md),
then:

```sh
pnpm install
pnpm tauri dev            # the app with hot reload
pnpm dev                  # the interface alone in a browser, with no backend
```

## Before every commit

Run the full check and make sure it passes:

```sh
./scripts/check.sh        # Linux / macOS
./scripts/check.ps1       # Windows
```

It runs `cargo fmt --check`, `cargo clippy -D warnings`, `cargo test`, `pnpm lint` (ESLint
and Prettier), `pnpm typecheck`, `pnpm test` (Vitest), `pnpm e2e` (Playwright) and
`pnpm tauri build --debug`. Use `--quick` / `-Quick` to skip the bundle build while iterating.
CI runs the same on Windows, macOS and Linux for every push.

## Tests

Every change comes with tests, at the level that fits it:

- **Rust unit tests** next to the code (`#[cfg(test)]`), and **integration tests** in
  `src-tauri/tests/it/` that drive the engine the way the app does, against the small fixtures
  in `fixtures/` (checked against values computed independently, not against DuckDB itself).
  SQL builders have `insta` snapshots: review changes with `cargo insta review`.
- **Vitest** for components, stores and helpers (`*.test.ts(x)` next to them).
- **Playwright** in `e2e/` for user flows, against the interface with the backend mocked
  (`e2e/tauri-mock.ts`, plus responses recorded from the real backend in
  `e2e/recordings/`). `e2e/a11y.spec.ts` (axe) and `e2e/keyboard.spec.ts` must keep passing:
  new screens should be reachable from the keyboard and meet WCAG 2.2 AA (D52).
- **Performance**: the large-file tests are `#[ignore]`d; generate the files with
  `pnpm fixtures all` (16+ GB, git-ignored) and run them as described in
  [docs/BENCHMARKS.md](docs/BENCHMARKS.md). `pnpm bench` runs the small suite and fails if a
  flow got more than 30 % slower than `bench/baseline/<os>.json`.

Never delete, skip or weaken a test to make it pass; fix the cause, or explain in the pull
request why the test was wrong.

## Conventions

- Commits use [Conventional Commits](https://www.conventionalcommits.org/),
  e.g. `feat(import): open csv.gz with instant preview`.
- Never commit large test data, build output, secrets or `node_modules`. Large fixtures are
  generated by `pnpm fixtures` (`scripts/gen_fixtures/`) into `fixtures/generated/`.
- Keep Tauri command handlers in `src-tauri/src/commands/` thin; the logic lives in the
  engine, sources and view modules, where it can be tested without the app.
- Never build SQL by concatenating user text: quote identifiers with `quote_ident` and bind
  values as parameters.
- Errors shown to people say what went wrong and what to do, in plain words.
- Colours come from the tokens in `src/styles/tokens.css` (the contrast test checks them);
  every action is a command, so it shows in the palette and the menus.
- Decisions that change the design or deviate from [BUILD_PLAN.md](BUILD_PLAN.md) are
  recorded in [docs/DECISIONS.md](docs/DECISIONS.md).

## Pull requests

Keep a pull request to one change, describe what it does and how you tested it (including
the OS you ran the app on), and update the docs it affects: README for features and
shortcuts, CHANGELOG under "Unreleased". Releases are made as described in
[docs/RELEASING.md](docs/RELEASING.md).
