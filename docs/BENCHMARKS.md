## v0.1.0 — linux-dev

**Startup** (release build, Xvfb with software rendering, 6 runs): the window
is mapped 0.12–0.16 s after launch; the UI is ready (React mounted, first IPC
call, logged as `frontend ready`) after 0.86–0.89 s. With `bigview comma.csv`
the file's rows are on screen after ~1.0 s.

**Idle memory** (release, no file open, 12 s after launch, PSS summed over the
`bigview`, `WebKitWebProcess` and `WebKitNetworkProcess` processes):

| Process | PSS | of which private (anonymous) |
| --- | --- | --- |
| bigview (Rust + DuckDB + GTK) | 104 MiB | 33 MiB |
| WebKitWebProcess (UI) | 115 MiB | 36 MiB |
| WebKitNetworkProcess | 22 MiB | 8 MiB |
| **Total** | **241 MiB** | **77 MiB** |

The budget is missed on PSS but met on private memory. Most of the rest is
shared library code mapped from disk: WebKitGTK and JavaScriptCore (~85 MiB
across the three processes), the bigview binary itself (29 MiB, mostly
DuckDB) and `libLLVM` (36 MiB), which is only loaded because Xvfb has no GPU
and WebKit falls back to llvmpipe software GL. On a desktop with a GPU driver
that part goes away. These pages are clean and shared with other WebKitGTK
apps. Opening a small file adds ~2 MiB. Tracked for the v1.0 performance
pass on all three OSes (Windows WebView2 and macOS WKWebView report memory
differently). See docs/DECISIONS.md, D25.

**Installer size**: the `.deb` and `.rpm` (19.4 MB) depend on the system's
WebKitGTK. The `.AppImage` (92.5 MB) bundles WebKitGTK and GStreamer so it
runs on any distribution; it cannot meet a 40 MB budget and is documented
instead (D24). The release binary is 50 MB uncompressed, most of it DuckDB.
Windows and macOS installers are built by CI (`tauri build --debug`) and
will be measured from release builds in the v1.0 release workflow.

**Grid scroll** (`pnpm e2e:perf`): headless Chromium, 1280×800, the backend
mocked with pages that answer after 7 ms (the measured 50M-row page time).
Steady wheel scrolling never waits for a page (prefetch); fast scrolling
(~60 rows per wheel event) crosses a page every few events. Page wait is the
time from the page request to rows ready, so it is an upper bound on how
long a region stays blank.

| Mode | fps | worst frame | page loads | page wait p95 / max |
| --- | --- | --- | --- | --- |
| steady scroll (100 px per event) | 60.0 | 17 ms | 0 | — |
| fast scroll (2,000 px per event) | 60.0 | 17 ms | 25 | 42 / 51 ms |
| fling (400,000 px per event) | 59.5 | 33 ms | 252 | 56 / 77 ms |

The real webviews (WebKitGTK, WebView2, WKWebView) are checked by hand in
each step's smoke test; frame timing there is part of the v1.0 pass.

**Small benchmark suite** (`pnpm bench`, best of 5 runs, dev profile, the
regression guard's flows):

| --- | --- |

| first_rows_100mb_csv_gz | 1,125 ms |

Run-to-run noise on this shared container is up to ~30% for the import
flows between batches (a few % within a batch), so the guard keeps the
fastest of 5 runs and compares against a baseline recorded on the same CI
runner type (`bench/baseline/<os>.json`), not against these numbers.

250 ms poll to end, so imports finished up to 250 ms late. Fixed (the thread
is woken when the import ends).

## v0.2 — views on 50M cached rows (linux-dev)

`cargo test -p bigview --test it perf_views_50m -- --ignored --nocapture` on
`sales_50m.parquet` imported into a cache database (9 columns: ids, dates,
timestamps, text, decimals, booleans). "First rows" is `open_view` plus the
first 500-row page, i.e. what the user waits for.

| View | Matching rows | First rows | Written in background | Page afterwards |
| --- | --- | --- | --- | --- |
| Sort by `customer` (text) desc | 50,000,000 | 1.19 s | 37.0 s | 18 ms |
| Sort by `order_date`, `unit_price` desc | 50,000,000 | 0.81 s | 20.3 s | 16 ms |
| Filter `quantity > 5` (broad) | 37,502,068 | 0.06 s (deep page before the write: 0.98 s) | 14.1 s | 12 ms |
| Filter `customer` contains "ab" (text) | 0 | 0.79 s | 0.7 s | 3 ms |
| Filter `quantity = 1` + sort `unit_price` | 2,500,387 | 0.38 s | 1.6 s | 4 ms |

Budgets: **simple filter on 50M rows < 2 s — met** (0.06–0.8 s to the first
rows and the count). **Sort 50M rows < 10 s — first and last rows met (about
1 s), full sort missed** on this 4-vCPU machine (20–37 s; the reference
laptop has twice the cores). The full sort runs in the background while the
first and last 10,000 sorted rows are already on screen; only pages in the
middle wait for it (D29).

Strategies measured before choosing (`perf_sort_strategies`): a sort of only
the row ids is faster (15.6 s) but fetching a page by id list then takes
1.1 s; writing full sorted rows to an in-memory table instead of the on-disk
scratch database saves little (26–55 s) and holds memory.

### Column profiles (v0.2 step 6)

`cargo test -p bigview --test it perf_profile_50m -- --ignored --nocapture`, same 50M rows,
warm cache. One profile is the stats query (count, nulls, min, max, mean, std dev, distinct —
HyperLogLog above 10M rows), the histogram and the 10 most common values.

| Column | Distinct | Profile |
| --- | --- | --- |
| `quantity` INTEGER | 21 | 1.21 s |
| `unit_price` DECIMAL(10,2) | ≈ 219K | 2.21 s |
| `order_ts` TIMESTAMP | ≈ 39.5M | 2.78 s |
| `customer` VARCHAR | ≈ 84K | 2.19 s |
| `country` VARCHAR | 9 | 0.44 s |
| `returned` BOOLEAN | 2 | 0.47 s |
| Header histograms, 7 columns (background) | — | 4.0 s |

Budget: **stats < 3 s per column on 50M rows — met**. Grouping the most common values by the
typed column and casting only the kept rows to text took `order_ts` from 7.5 s to 2.8 s (a
near-unique column builds a 39M-entry hash table either way, but of 8-byte keys instead of
strings). The header histograms read every column's range in one scan, then one scan per number
or date column; they load behind the grid and are cancelled by the next view change.

## v0.3 — exports and SQL on 50M cached rows (linux-dev)

`PERF_CACHE_DB=<db> cargo test -p bigview --test it perf_export -- --ignored --nocapture
--test-threads=1` (dev profile, warm cache): the same 50M rows (9 columns) as v0.2, exported
through `export::export` exactly as the app does (view query, `.partial` file and rename).
"Peak" is the growth of the process's peak memory during that export.

| Export | Rows | Time | Rows/s | File | Peak |
| --- | --- | --- | --- | --- | --- |
| Parquet (zstd), all rows | 50,000,000 | 7.6 s | 6.6M | 833 MB | +2.5 GiB |
| CSV, all rows | 50,000,000 | 23.9 s | 2.1M | 4,158 MB | +0.9 GiB |
| Parquet, sorted by `unit_price`, 4 columns | 50,000,000 | 12.7 s | 3.9M | 391 MB | +2.7 GiB |
| TSV, `quantity <= 2` | 4,998,023 | 1.2 s | 4.3M | 419 MB | +185 MiB |
| NDJSON, `quantity <= 2` | 4,998,023 | 1.8 s | 2.8M | 979 MB | +258 MiB |
| CSV.gz, `quantity <= 2` | 4,998,023 | 30.5 s | 0.16M | 111 MB | +810 MiB |
| JSON (array), `quantity = 1` | 2,500,387 | 1.0 s | 2.5M | 498 MB | +8 MiB |
| Excel, one full sheet | 1,048,575 | 14.7 s | 71K | 58 MB | +2 MiB |
| Excel, split into 3 sheets | 2,500,387 | 32.6 s | 77K | 138 MB | +64 MiB |

- **Excel** is written in constant-memory mode: memory stays flat however many rows (the
  rows stream from DuckDB batch by batch). It is the slowest format (one thread writing XML
  cells, ~75K rows/s); 1M rows take about 15 s.
- **CSV.gz** is bound by DuckDB's gzip writer, which runs on one thread (~14 MB/s of CSV). For
  big compressed exports Parquet is ~40× faster and smaller; a parallel gzip is a candidate
  for the v1.0 performance pass.
- **Parquet and sorted exports** use most memory (DuckDB buffers row groups and the sort), all
  within DuckDB's memory limit (50 % of RAM by default), spilling to disk past it.
- **Cold cache**: the first export after the 815 MB cache file had not been read for a day took
  79 s instead of 7.6 s — reading it from this container's virtual disk at ~12 MB/s. On a
  local SSD the first run costs about the time to read the file once.

SQL on the same rows, through the SQL panel's path (`sql_result`: the query is written once
into the scratch database, then paged):

| Query | Result rows | Time | First page |
| --- | --- | --- | --- |
| `GROUP BY country` with count and sum (8 groups) | 8 | 0.19 s | 2 ms |
| `GROUP BY customer` with count and avg (100K groups) | 100,000 | 1.44 s | 2 ms |
| filter + `ORDER BY unit_price DESC LIMIT 100` | 100 | 0.31 s | 6 ms |
| `SELECT * FROM sales` (every row as a result) | 50,000,000 | 11.5 s | 12 ms |

A query returning all 50M rows is written out before it shows (11.5 s here), so every row then
pages in milliseconds; queries that aggregate or limit, the usual case, are fast (D35).
